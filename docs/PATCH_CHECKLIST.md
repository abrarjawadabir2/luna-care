# LunaCare Patch Verification Checklist

Use this checklist before merging or deploying the LunaCare UI, flow, authentication, and security patch.

## Repository safety

- [ ] Existing features inspected before changes
- [ ] No unrelated files overwritten
- [ ] No unnecessary language or framework added
- [ ] No hidden backdoor, master password, universal OTP, hardcoded administrator, or debug bypass
- [ ] No service-role or provider secret in client code

## Server validation

- [ ] Every client-validated field is validated again on the trusted backend
- [ ] Unknown or excessive request fields are rejected
- [ ] Email, phone, OTP, dates, numeric ranges, enums, and text lengths have strict schemas
- [ ] User-generated text is rendered safely and cannot execute scripts
- [ ] Rejected-input logs contain only safe metadata, never raw passwords, OTPs, health notes, or tokens

## Brute-force and OTP protection

- [ ] Password login has server-side per-account and per-IP-hash controls
- [ ] OTP requests and OTP verifications have separate limits
- [ ] Progressive delay and temporary cooldown rules exist
- [ ] CAPTCHA or another challenge appears after suspicious activity
- [ ] Failed attempts cannot permanently lock out a legitimate account
- [ ] Successful authentication clears or reduces failed-attempt state
- [ ] Frontend timers are not the authoritative control

## Passwords and authentication

- [ ] A trusted authentication provider handles passwords, sessions, reset flows, OAuth, and MFA where available
- [ ] No password is stored in an application table
- [ ] No password or OTP is logged
- [ ] No MD5, SHA-1, plain SHA-256, reversible encryption, or regular string comparison is used for passwords
- [ ] Any unavoidable custom password storage uses Argon2id, a unique salt, and constant-time verification
- [ ] Legacy hashes are upgraded only after successful login

## Enumeration-safe responses

- [ ] Unknown email and wrong password return the same public message
- [ ] Password reset does not reveal whether an account exists
- [ ] Signup does not directly confirm that an email or phone number is registered
- [ ] Internal reasons remain in protected server logs only

## Backdoor and RBAC review

- [ ] No hidden login route exists
- [ ] No client-controlled admin flag grants privileges
- [ ] Users cannot change their own roles
- [ ] Administrator and super-administrator actions require verified server authorization
- [ ] Administrator MFA is enabled or included in the release plan

## Hashing and identifiers

- [ ] Non-password identifiers use server-side purpose-separated HMAC-SHA-256
- [ ] Email, phone, IP, device, user-agent, lookup, and audit purposes are separate
- [ ] HMAC secrets remain in backend secret management
- [ ] Purpose-separated hashes differ for the same normalized input
- [ ] A versioned secret-rotation plan exists

## Database and RLS

- [ ] RLS is enabled on every private table
- [ ] Policies are deny-by-default
- [ ] A verified session determines the user ID
- [ ] No private table uses a broad `USING (true)` policy
- [ ] Anonymous users cannot read private records
- [ ] Two test users cannot read or modify each other's records
- [ ] Privileged functions and `SECURITY DEFINER` functions have been reviewed
- [ ] The service-role key is absent from frontend source and bundles

## Secrets

- [ ] Source code contains no provider secret, service-role key, password, token, database credential, or signing key
- [ ] Generated frontend bundles contain no server-only secret
- [ ] Git history was scanned
- [ ] Any previously committed secret was rotated
- [ ] Local secret files are excluded by `.gitignore`
- [ ] CI includes secret scanning

## Dependencies

- [ ] Dependency audit was run
- [ ] Critical and high findings are documented
- [ ] Compatible security updates were applied and tested
- [ ] Breaking updates were left for explicit review rather than forced automatically
- [ ] CI includes dependency scanning

## File uploads

- [ ] Uploads are validated by approved MIME type and, where possible, file signature
- [ ] Size and count limits exist
- [ ] Object names are generated by the backend
- [ ] Private files live in isolated non-executable storage
- [ ] Sensitive files require signed access
- [ ] One user cannot retrieve another user's upload
- [ ] Active formats such as HTML, JavaScript, or unsafe SVG are rejected or safely sanitized
- [ ] Safe `Content-Type` and `Content-Disposition` headers are applied

## GPS, health data, and AI

- [ ] Exact GPS is off by default
- [ ] Location is requested only from Find Nearby
- [ ] Temporary coordinates are cleared after use
- [ ] Exact GPS is not stored or sent to AI automatically
- [ ] Private medical notes are not sent to AI without explicit selection and consent
- [ ] Sensitive note content is excluded from logs, analytics, crash reports, and audit events

## UI and period flow

- [ ] LunaCare design system is preserved
- [ ] Login, signup, OTP, and reset screens use calm generic messages
- [ ] Dashboard varies by user mode
- [ ] Flow-information screen includes spotting, light, medium, heavy, and very heavy
- [ ] Very heavy flow and red-flag symptoms show a non-diagnostic medical warning
- [ ] Back, home, loading, error, empty, offline, and permission-denied states work
- [ ] Reduced-motion preference is respected
- [ ] Mobile and desktop layouts are verified

## CI/CD

- [ ] Install from lockfile succeeds
- [ ] Lint passes
- [ ] Type checking or platform compilation passes
- [ ] Unit and integration tests pass
- [ ] Auth and RLS tests pass
- [ ] Secret scan passes
- [ ] Dependency scan is reviewed
- [ ] Migration validation passes
- [ ] Production build succeeds
- [ ] Critical findings block deployment

## Final release questions

- [ ] Can malformed data bypass server validation?
- [ ] Can login or OTP endpoints be spammed without backend throttling?
- [ ] Would a database dump reveal plaintext passwords or private note content?
- [ ] Do authentication errors reveal whether an account exists?
- [ ] Is authentication handled by a trusted provider rather than custom session code?
- [ ] Does the repository or Git history contain exposed secrets?
- [ ] Are known dependency vulnerabilities understood and addressed?
- [ ] Could an uploaded file become executable or cross user boundaries?
- [ ] Can one user access another user's private rows?
- [ ] Can a normal user promote their own role?
- [ ] Is exact GPS stored or sent to AI without consent?

## External review

- [ ] Manual security review completed
- [ ] Medical review scheduled or completed
- [ ] Privacy and legal review scheduled or completed
